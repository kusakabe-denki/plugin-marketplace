# セキュリティの自己チェック（security-self-check）

会社のルールでは、API キー・トークン・パスワードなどの秘密情報を、コード・`.env`・平文の環境変数に置かない。秘密は Google Cloud の Secret Manager に置き、API はできる限りキーを使わずサービスアカウントの IAM 権限で呼ぶ。このスキルは、プロジェクトの違反を見つけて、利用者の了解を得てから直す。

## 1. 全件を確認する

Bash ツールで次を実行する（`<プロジェクト>` は対象のフォルダの絶対パス）。

```
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "${CLAUDE_PLUGIN_ROOT}/scripts/session-check.ps1" -Full -ProjectDir "<プロジェクト>"
```

結果は「種類：ファイル:行」の一覧。秘密の値そのものは表示されない。**値をファイルから読み出して画面に表示したり、会話に貼ったりしない。**

## 2. 利用者に一覧を見せ、直す範囲の了解を得る

種類ごとに、次の直し方を説明してから作業する。了解を得ていない変更はしない。

| 種類 | 直し方 |
| --- | --- |
| `.env` に秘密情報 | 値を Secret Manager に移す（値は変えない・再発行しない）。Cloud Run のアプリは、デプロイ受付の `.kusakabe/app.json` の `secrets` に Secret の名前だけを書く（受付を使わない場合は `--set-secrets`）。移したあと `.env` からその行を消し、`.gitignore` に `.env` があるか確かめる |
| clasp のトークン（`~/.clasprc.json`）を読んでいる | トークンを直接読む処理をやめる。Cloud Run 上の処理はそのアプリのサービスアカウントの IAM 権限で呼ぶ。手元のスクリプトは `gcloud auth print-access-token` など正規の認証を使う |
| 直書きの API キー・トークン | コードから消し、Secret Manager から読む形にする。Google の API（Gemini 等）は、キーではなくサービスアカウントの権限で呼ぶ形（Vertex AI など）にできないか先に検討する |
| 直書きの秘密鍵・サービスアカウントの鍵ファイル | 鍵ファイルを使わず、サービスアカウントへのロールの付与で済ませる。鍵ファイルの削除と、Google Cloud 側の鍵の無効化は管理者に依頼する |

## 3. Secret Manager に置くとき

- 保存場所は東京（`asia-northeast1`）だけにする（会社のルール）
- Secret の作成とアクセス権の付与（そのアプリのサービスアカウントだけに `roles/secretmanager.secretAccessor`）は、権限の関係で管理者に依頼することが多い。必要なコマンドを用意して利用者に渡す
- 秘密の値はコマンドの引数に直接書かず、ファイルや標準入力から渡す

## 4. 直したあと

- もう一度 1 のコマンドを実行し、件数が減ったことを確かめる
- その秘密が過去に git にコミットされていた場合は、履歴に値が残っていることを利用者に伝える。履歴からの除去と、キーの再発行が必要かどうかは管理者と相談するよう伝える（**キーの再発行は利用者の指示がない限り行わない**）
- アプリを本番に出し直すときは、デプロイ受付（kusakabe-deploy）を使う

## してはいけないこと

- 秘密の値を画面・会話・コミット・ログに出す
- チェックを通すために、ファイル名の変更や除外の追加でごまかす
- 利用者の了解なしにファイルを書き換える・消す
